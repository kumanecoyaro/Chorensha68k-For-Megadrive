# 超連射68k (ver1.10) 解析メモ

対象: `CH68_110_1.xdf` 内 `CRS68K/SZ2.X`（Human68k .X 実行形式）。
アドレスはすべて SZ2.X をベースアドレス 0 でロードしたときの値。
逆アセンブルリストは `make disasm XDF=...` で `build/SZ2.lst` に生成される
（`tools/dis68.py`: capstone ベースの再帰下降逆アセンブラ。DOS/IOCS コール名、
X68000 I/O レジスタ名、リロケーション情報からのラベル付けを行う）。

## 1. ファイル構成

| ファイル | 内容 |
|---|---|
| `SZ2.X` | 本体。text $3C104 / data $DEB0 / bss $48C56、エントリ $398FC（XC ランタイム）→ `main` = $3892 |
| `assets.tgz` | 本体が miniz で展開して読む素材（`XSP_DAT/*`, `PCM_DAT/*`） |
| `XSP_DAT/*.sp, *.xsp` | 16x16 PCG（128 バイト/枚、4bpp、8x8 ブロックを 左上→左下→右上→右下 の順） |
| `XSP_DAT/*.ref, *.frm` | XSP 複合スプライト。ref = {枚数.w, frm オフセット.l}、frm = {dx.w, dy.w, PCG.w, 属性.w}（dx,dy は直前のスプライトからの相対） |
| `map.chp` | 32x32 ドットの「チップ」256 個。ヘッダ 8 バイト + 4x4 個の BG ワード（bit15 V反転, bit14 H反転, bit8-11 パレット, bit0-7 パターン） |
| `map.bg0 / map.bg1` | ヘッダ 16 バイト（幅 8, 高さ $400）+ チップ番号バイト列。8 チップ = 256 ドット幅 × 1024 行 |
| `bg_pcg.sp` | BG 用 8x8 パターン 256 個 |
| `bg_*.pal` | グラフィック画面用 256 色パレット（GRB555+I）。ステージ1は `bg_fb_nw.pal` を使用 |

## 2. メインループ（$38A2 内 L03A50〜）

1 フレームの処理順:

1. `fn_04338` ステージ進行（ステージ番号で `fn_06de4`(ST1), `fn_077b6`(ST2) ... へ分岐）、ランク $4A0C8 を 128 フレーム毎に +1
2. `fn_2cbda` 垂直同期待ち
3. `fn_05e50` 自機
4. `fn_06470` 自機ショット
5. `fn_04094` 全オブジェクト更新（連結リスト、各オブジェクトの +$24 の関数を呼ぶ）
6. 入力をリプレイバッファに記録、`fn_2cf3a` XSP スプライト出力
7. `fn_056ae` BG スクロール

乱数 `fn_345c8` は 1024 語の乱数テーブルを順に引くだけ（リプレイ互換のため）。
`fn_2fb06` は atan2（0=上, $40=右, $80=下）。三角関数表 `D_3e3bc` は
[速度 0..31][角度 0..255] の (dx, dy) 表（1/64 ドット単位、速度 1 で半径 64）。

## 3. 座標系

* オブジェクト座標は 16bit、1/64 ドット単位。XSP にはそのまま `>>6` して渡すので、
  16x16 セルの左上の画面座標は `(v>>6) - 16`、複合スプライトの中心は `(v>>6) - 8`。
* X68000 の画面は 256x256。自機の可動範囲は X: $400〜$4000, Y: $400〜$3F00。

## 4. オブジェクト

* プール $180 個 × $80 バイト、`fn_040b6` で確保、`fn_0410e` で解放（+$1A/+$1E 双方向リスト）。
* クラス表 `D_46460`: 16 バイト × $250 種 = {毎フレーム処理.l, 生成関数.l, 得点.l, 耐久力.w, …}。
  生成関数には呼び出し側スタック上の $80 バイトの「テンプレート」(x, y, 属性, 角度 +$54, 速度 +$64 …) を渡す。
* 主なフィールド: +0 x, +2 y, +4 パターン(ref 番号), +6 属性(パレット/反転), +8/+A 当たり判定半径(ドット),
  +$16 基本パターン, +$22 型, +$24 処理関数, +$3C/+$3E 速度, +$4C/+$4E カウンタ, +$54 向き, +$5C 耐久力, +$78 タイマ。
* ref 番号は XSP ファイルを読み込んだ順の通し番号（title=0, bullet32=1.., … player=$ABD, player2=$AC9, zako=$AD5, obj204_d, parts32, obj1a0, obj200=$B18 …）。

## 5. 自機 `fn_05e50`

* 入力はテンキー方向 1〜9 → 角度表 `D_489ea` → 速度 1 の三角関数表 × (速度 $30>>4 = 3)。
* 傾き $9048E: 左右入力で ±1/フレーム（±8 まで）、パターン = $ABD + ((傾き/8)+1)*2 + ((フレーム>>1)&1)。
* 出現: x=$2200, y=$5400、タイマ $5939A=$100。$80 までは毎フレーム y-=$40 で自動上昇、0 まで無敵（パレット点滅）。

## 6. 自機ショット `fn_06470`（超連射）

* ボタンの押下エッジを数え、タイマ $90496 が空いていれば 12 フレームの発射シーケンスを開始。
  押しっぱなしでは連射しない（連打前提）。
* タイマ & マスク(レベル0: 3) が 0 のフレームで発射:
  * タイマ≦7 なら中央弾: y-$100 から vy=$FD00（-12 ドット/F）、威力 = パワー×2
  * 左右一対の拡散弾: x±($200 + (タイマbit1?$100:0))、角度 = タイマ&~3、速度 9、威力 = パワー
* パワーレベル表 `D_489a6`（6 語 × 5 段階）。弾は 30 発のプール（y=0 が空き）。

## 8. 敵

### 型 $190 ザコ（init `fn_131d4` / 処理 L13298, zako.ref 16 方向）
* 出現時に自機方向の X 速度の半分を vx に、vy=$C0+乱数(0..63)。毎フレーム vy-=2（減速して上へ戻る）。
* 8 フレーム毎に向き $54 を ±16 ずつ目標へ回転（下降中は自機方向、上昇中は上）。
  向きが合っていて 16 フレーム毎・下降中・カウンタ < $20+ランク/4 なら型 $130 弾を発射（自機方向±乱数、速度 $30）。
* 被弾で即破壊、得点 250。

### 型 $1F0 中型機（init `fn_16fc0` / 処理 L170DC, obj200.ref #0, 128x80）
* y=-32 ドットから出現、耐久力 640、当たり判定 ±32x±24。
* タイマの下位 8 ビットが $60〜$E0 の間は停止、それ以外は 1 ドット/F で降下。sin/cos でゆらゆら揺れる。
* (t&$E7)=$80 で 3way 弾（型 $134, 間隔 8, 速度 $38）を左右 2 方向に、(t&$E7)=$A0 で大型弾（型 $132, 速度 $40）。
* 撃破で大爆発、得点 1000、アイテム（型 $1F8, 未移植）。

### 敵弾
* 速度ベクトル表 $4B91E = 速度16の三角関数表 × 設定値($10) / 256（`fn_05170`）、弾速度 × 表 >> 4。
* 自機との当たり: 型 $130 ±2x±4、$134 ±3x±5、$132 ±4x±6 ドット。

## 9. BG（`fn_05574`, `fn_056ae`, `fn_301f6`）

* BG は X68000 の BG 面ではなく、256 色グラフィック画面 2 ページにソフトウェアで描画している。
  チップ 1 個 = 4x4 タイル、各 8x8 タイルを展開表 `$305BE` で 1 ドット 1 ワード (パレット*16+色) に変換して書き込む。
* レイヤ 0 = map.bg0（手前、透過あり、初速 -$400 = 4 ドット/F）、レイヤ 1 = map.bg1（奥、-$100 = 1 ドット/F）。
  位置は 24.8 固定小数、速度は目標値へ 1/256 ずつ近づく。
* マップ行カウンタは減少方向に進み、`loop_end`($9046A) に達すると `loop_start`($90472) に戻る。
  ゲーム開始時 `fn_05906((stage-1)*8, $10)`。マップは面から面へ続けてスクロールする: `fn_058de(seg, $10)` は
  16 行のセグメント seg（行 1024-16(seg+1) 〜 1023-16seg）をループ範囲にし、n 面は seg 8n-8 〜 8n（8n はクリア時）を
  ループ、次の面はそのまま 8n から始まる（間の seg 8n-1 はクリア中に通過）。1 面は seg 0〜8（実測でも一致、
  ゲーム開始時の一瞬だけ seg 56 も描く）。遠景は 1/4 の速度なので、次の面の始めはまだ前の面の遠景が見えている。
* BG パレットは 9 本（D_3d558: fb_nw, fy_np, fy_nr, fb_np, fr_nb, fb_ny, st0, dark, lite）を B_4a31c + k*$200 に読み、
  n 面の状態 $100 で前の面の色から n-1 番へ $80 フレームかけてフェード（fn_0479a。1 面は st0 から）。
* 4 ラインごとに 1 チップずつ描画して負荷を分散している。

## 10. 効果音

* `PCM_DAT/SZ2_PCM.CNF` に PCM 番号 → ファイル / STAT / PR の対応がある。STAT は IOCS `_ADPCMOUT` の d1
  （上位バイト = サンプリングレート: 4 = 15.625 kHz, 3 = 10.416 kHz、下位 = パン）。
* `fn_034ae(番号)`: そのフレームの要求より PR が低ければ無視、以上なら置き換え（B_8401a）。
* 使用例: 自機ショット $20、ザコ爆発 $01、中型機爆発 $03、ショット命中 $42、自機被弾 $28 / $29。

## 11. BGM（MDX → YM2612 + DCSG）

* `BGM_DAT/SZ2_BGM.CNF` は MDC（MCDRV 形式）を指すが、同じ曲の MDX が `BGM_DAT/original` にあるのでそちらを使う。
  13 曲、各 16 トラック（PCM8 拡張形式）だが、使われているのは FM の A〜H の 8 トラックのみ（ADPCM トラックは空）。
* ほぼ全チャンネルにデチューン約 -128（-2 半音、±10 程度ずらしてコーラス）が掛かっている。
  X68000 の OPM は 4 MHz 駆動（標準 3.58 MHz より約 +1.92 半音高い）なので、その補正。
  MD 版はノート番号 n を MIDI n+15 として YM2612 / DCSG の周波数を計算し、デチューン込みで X68000 実機と ±8 セントで一致する。
* 繰り返し: $F6 n 00 で開始（2 バイト目は実行時カウンタ）、$F5 の相対オフセットは $F6 直後を指す。
  $F4（最終回で脱出）の相対オフセットは対応する $F5 のオペランドを指すので、脱出先はそこから 2 バイト先
  （以前これを誤って $F5 のオペランド $FF をテンポ命令として実行し、1 面の曲が 55 秒付近から崩れていた）。
* $F7（&）は「次の音符の終わりでキーオフしない」。その次の音符はキーオンせず音程だけ変える（スラー / タイ）。
  q8 は次の音符（または休符）の直前までキーオフしない。
* @v は減衰量（0 が最大音量、実データは 0〜17）。v0〜15 は MXDRV の音量表で TL 加算値に変換。
* ソフトウェア LFO（MP / MA）のパラメータは 1 ティックあたりの変化量（1/256 単位）。波形番号 +4（4〜6）は変化量 256 倍
  （ドラムの音程の急降下: キック MP6,80,-204 は 1 ティック -3.2 半音。以前は無視していてバスドラが太鼓のように鳴っていた）。
* チャンネル割り当て（`tools/convert_bgm.py` が曲ごとに決定）: ノイズ（OPM レジスタ $0F / $ED）を使うチャンネル、
  他チャンネルの遅延コピー（エコー）、音域の高いチャンネルを優先して 2ch を外す（DCSG へ回す経路もドライバに
  残してあるが現在は未使用）。
* YM2612 の $A4-$A6（ブロック / F ナンバー上位）は全チャンネル共通のラッチで、続く $A0-$A2 の書き込みで確定する。
  必ず $A4 → $A0 の対で書くこと（片方を省略すると他チャンネルの値で鳴る）。
* YM2612 はレジスタ / DAC 書き込みの後しばらくビジーになり、その間の書き込みは失われることがあるので、
  Z80 は毎回ステータスのビジービットを待ってから書く。
* レジスタの重複書き込み省略では「未書き込み」を値と別に管理すること（以前は 0xFF を初期値にしていて、
  D1L/RR=$FF のような値が書かれずに残った）。
* DAC は FM6 のパン（$B6）を共有するので、効果音の再生中は中央に固定し、終了時に BGM の値へ戻す。
* 効果音の音量: 全効果音に同じ倍率（2.5 倍、半分を超える所はソフトクリップ）で原作の音量比を保つ（ショット p_fire1 は
  大爆発の 1/8）。優先度 $44 以上の効果音（自機のボム p_bom、大爆発、ミス、アイテム）の再生中は BGM の FM を
  さらに 7.5 dB 下げる（ダッキング: DAC は FM 1 チャンネル分の音量しかない）。自機のボムは原作どおり 8 フレームごとに
  5 回 p_bom を鳴らし直す。
* 演奏はティック単位（Timer-B 値 → 1 フレームあたりのティック数表）で、VBlank の実回数で進める。
* YM2612 への書き込みは Z80 がキュー経由で行う（DAC へのサンプル書き込みとアドレスラッチを奪い合わないため）。

## 12. 原作コードの直接実行（tools/relocate.py）

ゲームロジックは手で移植せず、SZ2.X の 68000 コードを MD 上でそのまま動かしている。

* メモリ: .X のリロケーション表（全絶対アドレスの位置）を書き換えて、text / data → ROM $10000 + a、
  使用する BSS 範囲 → RAM $FF0000〜 に詰めて配置。BSS の使用範囲はリロケーション先を関数ごとに集計して決めた
  （グローバル変数・自機ショット・オブジェクトプール $49FB4〜、ステージ / 自機状態 $5931E〜、
  BG / ショット状態 $90252〜 ほか）。XSP 作業領域・リプレイバッファ・GVRAM 描画用マップ展開領域などは不要。
* オブジェクトプールは 383 個 → 128 個（`fn_04034` の個数を書き換え、RAM 16 KB）。
* data 部で書き込まれる変数: クラス $40 の処理関数（`fn_044a2` がステージ毎に設定）、パレットアニメ状態。
* text 部に状態を持つライブラリ: 当たり判定（`fn_2f3cc`〜`fn_2f704`、グリッド $2F722 と矩形 $2F822 を
  PC 相対で参照）、乱数（`fn_345c8`、インデックス $345E0）。ルーチンごと RAM へコピーして使う。
* 範囲の終端アドレスを指すリロケーションは別シンボルの先頭（例: $2F922 = `fn_2f922`）なので、
  範囲外として扱うこと（範囲の「1 つ後」を同じ範囲に含めると誤動作する）。
* マップ（B_8C252、2 層 × $2000）は ROM 上の map.bg0/bg1 を直接参照させる（`fn_053ba` のヘッダ解釈結果
  = 幅マスク 7、高さマスク $3FF、行シフト 3 をフックで設定）。
* フック（関数先頭 6 バイトを `jmp HOOK_BASE+6*i` に書き換え）:
  XSP（`fn_2c9fe` xsp_set, `fn_2ca2c`, `fn_2ca5e` xobj_set; `fn_2ca5a` は movem して `fn_2ca5e` へ
  落ちるので原作のまま）、垂直同期 `fn_2cbda`、XSP 出力 `fn_2cf3a`、IOCS 入力（`fn_39dac` BITSNS,
  `fn_39e16`/`fn_39e58`/`fn_39e7a` JOYGET）、リプレイ入出力（`fn_00f26` 方向, `fn_01048` ボタン）、
  パレット（`fn_05224`, `fn_05a3a`, `fn_051b8`）、BG（`fn_053ba` 読み込み, `fn_301f6`/`fn_303a2` チップ描画）、
  テキスト（`fn_2f06a` 1 文字, `fn_2f2aa` 消去）、音（`fn_034ae` 効果音要求, `fn_03590` BGM, `fn_03872` フェード）、
  ゲームオーバー後の `fn_0132c`（ネームエントリ等）ほか。
* XC のレジスタ規約は d0-d2/a0-a2 破壊、gcc は d0/d1/a0/a1 破壊なので、C から原作関数を呼ぶ時は
  `ocall`（d2-d7/a2-a6 を保存）を通す。レジスタ渡しの XSP 関数のフックは原作が保存するレジスタを全部保存する。
* 起動: 原作のトップレベル `L03e60`（設定の初期値 → タイトルメニュー `fn_02dac` → `fn_038a2` 1 ゲーム →
  タイトル）をそのまま動かす。メニュー: START / CONTINUE / CONFIGURE / CREDITS / exit（`fn_02dac` は 0 開始、1 コンティニュー、
  4 exit、5 放置時のリプレイデモを返す）。パッチ: exit で終了しない（$03f46）。
  タイトルメニュー `fn_02dac` は `src/title.c` に置き換え（EASY / NORMAL / HARD・CONTINUE・CREDITS・exit。CONFIGURE は
  X68000 の 512 ドット幅テキスト画面に X68000 用の設定なので無し）。難易度: GAME LEVEL B_4a0f8（0 normal / 1 impossible）と
  敵弾速度 TD_SPEED B_4a106（隠し設定、$10）: EASY = normal + $0C、NORMAL = normal、HARD = impossible。
  `fn_2ff62`（垂直帰線を n+1 回待つ: タイトル、ゲームオーバー、ポーズ）は VBlank 待ちに、`fn_2cf40`（BG スクロール無しの
  XSP 出力: タイトル）もフック。待っている間に書き換わったテキスト（2 行目以降はスプライト）は直前の画面の
  スプライトの前に入れ直す。`fn_3975a`（IOCS $B2 グラフィック画面の表示 ON/OFF、d1 = 表示ページ 0 / 3）: 原作はゲーム開始時に
  OFF → 面の初期画面を全部描く（`fn_05574`）→ ON の順で、最初のフレームから画面が埋まっている。
  OFF で両プレーンを消して Plane B を隠し（名前表を空の Plane A に向ける）、ON で表示する。
  タイトル（`x_title_menu`）も原作どおり最初に OFF にする（ゲームオーバー後に前の BG が残らない）。
* ゲームオーバー: `fn_038a2` が「GAME  OVER」を表示して待ち（ボタンか 449 フレーム）、`fn_0132c`（ランキング・ネーム
  エントリ）を原作のまま動かす（`x_game_over` → `src/hooks.s` orig_0132c）。ランキング B_49fb4（10 件 x 24 バイト: 得点・
  面・名前 12 文字）の初期値は ETC_DAT/SCORE.DAT（relocate.py が初期 RAM に入れる）。SCORE.DAT の書き込み `fn_01106`、
  グラフィック画面の IOCS（$B1 / $B4 / $BA / $B5、`fn_39764`）、XSP の VBlank 数待ち `fn_2cbb8` は何もしない。
  1 位のときのリプレイ保存（fn_00c9c の中の L00dba へ直接飛ぶ）は飛ばす（$01fb2）。
  X68000 のテキスト画面は 32 行で、ネームエントリは 1〜30 行目を使う: その間は画面の 1〜27 行目に
  テキストの 1, 4, 6〜30 行目を出す（`text_map`）。
* タイトル放置: 原作の `fn_02dac` どおり $180 フレーム操作が無いとテキストを消して `fn_011ce`（ランキング、10 行目から）
  を $100 フレームかボタンまで表示（テキストは 1 行上に詰める）。原作はその後リプレイデモ（未移植）、ここではメニューに戻る。

  ずれて二重に見えないよう）。テキストの再描画で残すスプライトは優先度 低のものだけ（テキストは高）。

## 13. スプライト（XSP の置き換え）

* PCG 番号は全 .sp / .xsp を読み込んだ順の通し番号（sz2_main.sp, rot32.sp, rot16.sp, debris.sp, mob.sp,
  title.xsp, bullet32.xsp, …）。ref 番号も .ref の読み込み順の通し番号で、frm の PCG 番号には直前に読んだ
  PCG ファイルの先頭番号が足される（ele_arc は rot32 の $50、debris1 は debris.sp の $C4 を明示指定）。
* info: bit15 V 反転、bit14 H 反転、bit11-8 パレット、bit5-0 優先度（大きいほど手前）。xobj_set の info は
  各 frm の info と XOR される。座標は 1/64 ドット、XSP のスプライト座標 (16,16) が画面左上。
* 変換: PCG 1 枚 = MD の 2x2 スプライト（X68000 の PCG と同じタイル順・同じ 4bpp 形式なのでそのまま）。
  frm が 2 枚以上の ref は合成して 32x32 までのブロックに切り直す（大型機 1 機 40 枚 → 十数枚、
  ザコ・自機オプション・砲台パーツ・大型弾など 32x32 に収まるものは 16x16 x 4 枚 → 1 枚）。
  反転を多用する爆発・破片・衝撃波は合成すると ROM が 2 MB を超えるため、PCG 単位のまま VDP の反転を使う。
* VRAM: 4 タイル枠 160 個 + 16 タイル枠 30 個のキャッシュ。（ブロック, パレット）をキーにハッシュ表で管理し、
  未登録ならパレット変換表を通してステージングバッファへ展開、VBlank で DMA。
* パレット: X68000 のスプライトパレット 16 本を、使用頻度で重み付けした k-means で MD の 2 本へ割り当て、
  1 バイト（2 ドット）単位の変換表で色番号を付け替える。
* テキストの表示: スコア行はウィンドウ面。2〜28 行目は Plane A が大型敵・エフェクトを出していない間は
  Plane A に書く（H32 のスプライトは 1 ライン 16 枚まで: 1 文字 1 スプライトではクレジットや面クリアの
  ボーナス表示の長い行が欠けていた）。Plane A を使っている間だけ 8x8 スプライト。
  ゲームのスプライトは優先度 低（原作どおりテキストがスプライトより手前）、テキストは高。
* テキスト: SZ_TEXT.pcg は 1 文字 4 プレーン（プレーン p は +$20*p、各 8 行 2 バイト間隔）。
  テキストパレットは `fn_051b8` が _TPALET2 でパレットファイルの 33〜47 色（= スプライトパレット 2）を
  設定するので、フォントはスプライトパレット 2 の変換表で MD パレットへ割り当てる。
* 削減: 爆発の数は原作のまま（生成も描画も間引かない）。爆発用の枠（FX_MAX = 28 枚）を画面上の爆発の数で
  均等に分け、どの爆発も必ず描く。敵の爆発（expl4、PCG 単位のスプライト）は、そのフレームの枚数が
  自分の取り分に収まれば全部（少ないときは原作どおり）、収まらなければ PCG を 1 枚おきに描く。
  （32x32 への合成は、コマごとに最大 2.4 KB の VRAM 転送が要り、同時 3 個以上で破綻するので不採用）
  パーティクル（敵破壊時に飛び散るパーツ = クラス $81〜$83 の debris.sp、火花・破片 = クラス $122〜$124）は
  生成を常に拒否し、spark / debris1 / debris2 の ref と debris.sp の PCG も描画しない。
  ボムの稲妻（ele_arc $87〜$B4、PCG 単位のスプライトで 1 本 37〜57 枚）は PCG を 1 枚おきに、
  フレームごとに交互に描く。
* 自機ショット（優先度 $3A、PCG $98 / $99）は記録時に優先度 $3D へ付け替え、敵弾（$3C）より先に描く。
  64 枚を超えたとき削られるのは敵弾・レーザーの側（2 面ボスのレーザーで自機ショットが消えていた）。
* 自機（優先度 $3E）は $3F（テキスト・ボム）の直後に描き、$3F は 64 枚のうち 4 枚（`PLAYER_ROOM`、自機の
  ref は最大 2 ピース）を残す。優先度の付け替え表 `pr_map`（xsp_fast.s）は GAS m68k で `|` がコメント文字の
  ため `0x80 | SMOKE_PR` と書いた行の後半が消え、表の $39〜$3F に後続の命令のバイトが入っていた（敵弾 $3C が
  $44 = 自機より手前、自機ショットが $0C）。敵弾が 56 枚を超えると自機が表から押し出されて消えていた。
  `+` で書き、表が 64 バイトでなければアセンブル時にエラーにする。TEST_PLCHK ビルド（`plchk`）で
  自機のピースが VRAM / スプライト表にあるかをフレームごとに検査（修正後 1〜4 面 9000 フレームで欠落 0）。
* xsp_build は空の優先度を 4 命令で飛ばす。
* 敵弾（$3C、レーザーの弾片を含む）は敵本体（$34、敵弾より後に描く）の分を残す: 敵弾の段の上限は 64 から
  $34 の呼び出しのピース数（最大 `ENEMY_ROOM` = 16）を引いた数（`enemy_room`）。レーザーを撃つ雑魚が複数いると
  レーザーが全スプライトを使い、雑魚が全部消えていた（TEST_DROPCHK: 4 面 16000 フレームで敵本体の欠落 約 430 → 45）。
  削られた下側の敵弾はダブラが拾う。
* 真下へ撃つレーザー（縦の弾片 PCG $50 太 / $59 細。4 面のレーザー雑魚）: 同じ優先度の直前の呼び出しが同じ PCG・
  同じ属性・同じ x で 16 ドット上か下なら、2 枚を合成済みの ref（`VLASER_REF` = NREF - 2 / - 1、16x32 の
  スプライト 1 枚、convert_sprites.py `VLASER_PCGS`）1 件に置き換える（記録時、h_xsp_set_main。ボスの有無に
  関係なく、実行時の合成もしない）。1 本 7 枚が 4 枚に。
* ボスが斜めに撃つレーザー（$51〜$58 太、$5A〜$5F 細）: ボス用の経路（h_xsp_set_boss）が見つけた隣り合う 2 枚は、
  反転を戻したずれ（2 枚目 - 1 枚目）で表 `pair_lut`（[PCG - $50][dy + 16][dx + 16]、u16、ROM）を引き、
  あれば変換時に合成した ref（`PAIR_REF` + 値 - 1）1 件にする。合成するずれは PCG ごとに、長さ 14.5〜17.5 ドットで
  弾片の向き（画素の主軸）から 11 度以内のもの全部（逆順も。2 面・3 面ボスで見たずれは 9.3 度、15〜17.1 ドット以内。
  486 通り、ブロックは逆順と共有）。2 面ボス第 2 形態の細いレーザーも含め実行時の合成 0 件。
  表にないずれだけ従来の実行時の合成（下）。
* スプライトのキャッシュのキー（ブロック << 4 | パレット）はボムの網掛け用（`MESH_KEY` = $E000〜）より下:
  ブロックが 2788 → 2916 に増えて $B000 にしていた網掛けの範囲に食い込み、3 面ボスで画面が崩れた（静的アサートで検査）。
* 3 面ボス第 1 形態の針弾の流れ（$86、パレット 1: 8 ドット離れた 2 列が約 10 ドットずれて並ぶ、左右から挟む
  レーザー）: h_xsp_set_main がボス用と同じ 4 件さかのぼる探索で隣の列の 1 発を探し、`pair_lut` の 17 行目
  （dx ±8、dy 9〜12 と逆順）にあれば 2 発を合成済みの 16x32 の ref 1 件にする。
* 3 面ボス第 1 形態の太いビーム（ref 1〜3: 16x32 の炎。8 ドット間隔の 3 列が 16 ドットずつずれて並ぶ）:
  h_xobj_set で同じ優先度の直前 4 件に同じ ref・属性・高さで 16 ドット左右のものがあれば、2 つを合成済みの
  32x32 の ref（`LBEAM_REF` + ref - 1、convert_sprites.py `LBEAM_REFS`）1 件にする（1 周期 3 枚 → 2 枚）。
* ダブラ（ボス戦の弾幕）: 最大 40 発（RAM は CPU 変換のバッファ 4096 → 3584 バイトから）。敵弾の段で表が
  満杯になった後も、残りの単体 PCG の弾のうち DBL_B より下のものはダブラのリストへ（表の枠は要らない）。
  敵弾の ref のピース（上の 16x32 の対）も DBL_B より下ならダブラへ（大きさを保つ）。下の弾が上の弾の枠より
  多いときは、DBL_A までに描き終わる表の全エントリ（敵・自機ショット・エフェクトも）を枠にする。
  3 面ボス第 1 形態（TEST 計測）: 表に入らず消えた単体の弾 7.7% → 0%、枠不足で捨てた下の弾 3.4% → 0.3%
  （後半の弾幕の濃い区間は 4.5% / 2.8% 残る: 上側の 64 枚と 1 ライン 16 枚の上限）。
* ボス・中ボスのレーザー（PCG $50〜$5F、16 方向 x 太細の 16x16 を並べた弾列）は、同じ PCG・同じ属性で
  32x32 に収まる 2 発を 1 枚にまとめる。xsp_set のフックは RAM のベクタ（`xsp_set_vec`）経由で、
  ボス・中ボス（pl_refmap の ref: 蟹・obj200・obj204・obj205）がいる間だけ `h_xsp_set_boss`
  （レーザーなら同じ優先度の直前 4 件から相手を探し、見つかれば 1 件目の id bit14 と info bit12 を立て、
  相対位置を座標の端数ビットへ）、それ以外（道中・ザコ）は `h_xsp_set_main` に直行してレーザーの判定もしない。
  xsp_build は対の印を文字セルの分岐（id bit14）の中で見るので、通常のスプライトの経路は増えない。
  2 枚の合成（`pair_put`、アセンブラ、約 4 万サイクル。C 版は 1 枚 10 万サイクル超で 1 面ボスが 1/3 の速度に
  落ちた）は 16 タイル枠の末尾 6 個にキャッシュ（キー: PCG, 属性, 相対位置）、1 フレーム 1 回まで、
  ヒットで貯まるクレジット（64 で 1 回、ボス出現時に 6 回分）がある時だけ。弾列の間隔は掃引で毎フレーム
  変わりほとんど再利用できないので、合成しない対は今までどおり 2 枚で描く。
* RAM: スタック（$FFFE00 から下へ）は約 2 KB 要る（足りないと変数が壊れた）。md.ld で _ebss ≦ $FFF600 を検査。
* ミサイル・ホーミング弾の煙（クラス $121、生成 `fn_10972`、処理 L109d0）: 1 個の煙は経過値 $4E を毎フレーム

  （relocate.py）: 生成間隔（粗密）はそのまま、尾の長さとスプライト数が 1/4。煙（PCG $30〜$37、優先度 $38 / $3B）は
  記録時に優先度 $32（敵 $34 の後ろ）へ: スプライトが足りないとき敵より先に削られる（`pr_map`）。
* 起動時の初期化 `fn_05224`（ファイル読み込み・パレット・ライブラリのフック登録）はフックで置き換えている

  書き換える（`_hint`、表示中の VRAM 書き込みは 1 ライン 2 エントリ程度）。新しい表が来ないフレームは VBlank で上の弾に

* 4 面: BG セット（bg_fb_np、seg 23〜33）。4 面クリアで 1 面へ（$0a4de を subq.w #3）。後半（状態 $210〜$240）の

### ROM からの DMA
* VDP の DMA は転送元の 128 KB 境界をまたげないので `dma_rom` が境界で 2 回に分ける。2 回目の転送元を 32 ビット
  ポインタ + ワード数 / 2 で進めていたため、境界までのワード数が奇数（データの先頭が 4 バイト境界にない時）だと
  1 ワードずれ、境界をまたぐ事前変換ブロックのタイルが壊れていた（2 面の obj203 $B21: pre_tiles が $1B258E に置かれ、
  キー $8118 のデータが $200000 をまたいでいた。ユーザーのセーブステートの VRAM とキャッシュ表で確認）。バイト単位で計算。

### 処理落ち対策（PicoDrive で実測、無敵・連射: 1 面 68% → 94%、2 面 81% → 90%。フレームスキップは使わない）
* VRAM の割り当てをステージごとに: BG タイル（1 面 149 / 2 面 330）の直後から 4 タイル枠（1 面 121 / 2 面 65 個）、
  16 タイル枠 40 個（28 個では 2 面の中ボスの胴・腕の 16 タイルブロックが読み直し続けた。48 個で頭打ち、56 個だと
  2 面の 4 タイル枠が尽きる）、タイル 1234〜1535 が大型の敵の絵。BG セットの切り替えでキャッシュを空にして配置し直す
  （`xsp_cache_layout`）。固定 96 個にしていた間は 2 面の中ボスで毎フレーム 4 KB の読み直し（スラッシング、
  VBlank からはみ出す DMA が約 150 ライン）が起きていた。
* 記録: xsp_set の記録は d4 だけ退避、優先度リストの先頭表と次リンク表を 128 バイト離して 1 本のアドレスレジスタで
  扱う（メモリ間 move）。xobj_set は記録をインライン化し、Plane A が見る ref はビット表（pl_refmap）で判定。
  単体 PCG は記録時に画面外を除いているので構築時の横のチェックを省略。文字スプライトが無いフレームは text_sprites を飛ばす。
* 2 面中ボス区間（大きい弾が多くスプライトが常に 64 枚）はまだ 36〜47 / 60、1 面ボス撃破の瞬間は 28〜45 / 60。
  原作ロジック（当たり判定は RAM 上の原作ルーチン）とスプライト構築の合計が 1 フレームを超える。
* Plane A のエフェクト（スプライトより先に読み込む）は 4 タイル枠の半分まで、前のフレームで使った枠は追い出さない
  （ボス撃破の大爆発が画面上のスプライトのタイルを追い出し、読み直しが間に合わず欠けていた）。
* フレームの重ね合わせ: 前のフレームの表示（VBlank）待ちを x_vsync（ゲーム処理の前）から x_xsp_out
  （スプライト構築の直前）に移した。1/60 秒を少し超えたフレームが 30 fps に落ちず、超えた分だけ遅れる。
* スプライトのタイル変換: ステージ 1 で読み込まれる (ブロック, パレット) 832 組（`tools/hot_keys.txt`、
  uctrace `--keys-dump` で採取。2 面の 274 組は TEST_KEYLOG ビルドを PicoDrive で動かして採取: 2 面 81% → 88%）を convert_sprites.py が変換済みで ROM に持ち（377 KB）、キャッシュへは
  ROM から直接 DMA する（1 フレーム 4 KB まで）。CPU 変換は表にないものだけ。
* xsp_set の記録をフックに直接書いた（record 呼び出しとレジスタ退避を省略）。xobj_set は Plane A が探す ref
  （エフェクト・蟹・ボス）の呼び出し番号を控え（`pl_ix`）、plane_frame は全呼び出しを走査しない。
  Plane A の静止画の書き直しは中身のある行だけロングワードで消す。
* キャッシュの枠（4 / 16 タイル）がそのフレームで埋まったら、以後の読み込みは枠を探さずにすぐ諦める。
* 音楽ドライバ: チャンネルループはポインタで回し、ソフトウェア LFO はティックごとに数えるだけにして
  VBlank ごとにまとめて進める（三角波はインライン）。TL（fm_tl）と周波数（set_pitch）はキューへ直接書き、
  音色が同じならキャリアの TL だけを見る。
* 合成 BG プールの空き数を数え、満杯のときは 96 枠を走査せずにすぐ失敗する（4 面で merge_cell 13% → 6%）。
* 計測: FRAME_PROBE ビルド（ゲーム処理 / スプライト構築 / VBlank 内の音楽の時間を走査線数で記録）、
  uctrace `--fncount 関数`（1 回あたりの命令数）、`--profrange` / `--abs`。
  tools/ucprof.py はブロック単位で数える高速版（uctrace の約 20 倍）: `--range 開始,終了`（ゲームフレーム）、
  `--hot 関数`、`--fn 関数`（1 回あたりのバイト数）。
* 取り消した呼び出しは部品 0 個の ref（spr.h `REF_EMPTY`）に付け替える。
* VRAM: 合成 BG タイルのプール 96 枚は H32 で使わない領域（ウィンドウ面の 2 行目以降、スプライト表の 65 個目以降、
  全画面スクロール表の残り）に置き、スプライトキャッシュは 4 タイル枠 128 + 16 タイル枠 28。

## 14. 処理時間

* 1 フレーム（262 ライン）の内訳（通常の場面）: 原作ロジック 約 80 ライン、スプライト展開 約 80 ライン、
  VBlank 割り込み（表示更新 7 + 音楽・効果音 40）。原作の X68000 は 55.5 Hz、MD は 59.9 Hz。

  スライドとドラムのスイープ（波形 +4）は毎 VBlank）、同じ音色・同じ音量の再設定は書き込まない。
* 4 面（PicoDrive、10000 フレームでの到達ゲームフレーム、3 通りの入力の平均）: 5581 → 合成 BG プールの修正 5845
  → 音楽ドライバの修正 6307（+13%）→ pr_map の修正・空の優先度の読み飛ばし・__mulsi3 の除去 6511。音楽なしのビルドは 7463 で、音楽は VBlank あたり約 46 ライン（修正前 53）。

  Plane A の静止画にできない。
